# 테스트 작성 및 보고 (api/, web/)

결과물:
- `api/`는 Vitest + Supertest 테스트 (`api/src/**/*.test.js`)
- `web/`는 Vitest + React Testing Library 테스트 (`web/src/**/*.test.tsx`)
- 테스트 실행 결과 보고서: `reports/test/<날짜>-<기능ID>-<브랜치>.md`

## 진행 순서

### 1단계. 입력 자료 확인
- `docs/requirements.md`의 완료 기준을 테스트 케이스의 기준으로 삼는다
- API 동작을 테스트할 때는 `docs/api-spec.md`(있으면)의 요청/응답 정의를 참고한다
- 어떤 기능(T/S/N 번호)을 테스트할지, 대상이 `api/`인지 `web/`인지 먼저 확인한다 (불명확하면 질문한다)

### 2단계. 테스트 케이스 뽑기
- 완료 기준 한 문장당 최소 1개의 테스트를 만든다
- 정상 케이스 + 경계/예외 케이스(빈 값, 없는 id, 빈 목록 등)를 함께 포함한다
- 이미 있는 테스트 파일이 있으면 먼저 읽고 중복 테스트를 만들지 않는다

### 3단계. 테스트 작성
- 테스트 이름은 완료 기준 문장을 그대로 반영한다 (예: `it("빈 값이면 추가되지 않는다", ...)`)
- `api/`: `app.js`가 export하는 Express 인스턴스를 Supertest로 호출해 상태 코드와 응답 바디를 검증한다 (`app.test.js` 참고)
- `web/`: 사용자 동작(클릭, 입력) 기준으로 테스트하고 내부 구현 세부사항에 의존하지 않는다 (RTL의 `getByRole`/`getByText` 등 사용, `App.test.tsx` 참고)
- 테스트 간 상태가 공유되지 않도록 각 테스트 전/후 데이터(DB 파일, 목 등)를 초기화한다

### 4단계. 실행
- `api/` 디렉터리에서 `npm test`, `web/` 디렉터리에서 `npm test`로 실행한다 (루트에서는 `npm test`로 둘 다 실행 가능)
- 실패하면 테스트가 아니라 요구사항/완료 기준과 비교해 어느 쪽이 맞는지 먼저 확인한 뒤 수정한다
- 아래 "결과 보고서 작성" 전까지는 테스트가 통과(또는 의도적으로 실패/스킵한 사유가 명확)한 상태여야 한다

### 5단계. 결과 보고서 작성
모든 테스트 실행 뒤에는 **항상** `reports/test/` 아래에 보고서를 남긴다.

- 파일 경로: `reports/test/<YYYYMMDD>-<기능ID>-<브랜치>.md`
  - `<기능ID>`: 이번에 테스트한 요구사항 번호(예: `T1`, 여러 개면 `T1-T3`처럼 묶는다). 특정 요구사항에 속하지 않으면 `general`
  - `<브랜치>`: 현재 git 브랜치명. `/`가 포함되어 있으면 파일명에서는 `-`로 바꾼다 (예: `setup/2-scaffold-ci` → `setup-2-scaffold-ci`)
  - 예: `reports/test/20261102-T1-setup-2-scaffold-ci.md`
- 브랜치명과 커밋 해시는 `git branch --show-current`, `git rev-parse --short HEAD`로 확인한다
- 보고서는 다음 형식을 따른다:

```markdown
# 테스트 보고 — {기능ID}

| 항목 | 내용 |
|------|------|
| 보고자 | {에이전트/사용자 이름 또는 "test-writer 스킬"} |
| 일시 | {YYYY-MM-DD HH:mm} |
| 브랜치 | {브랜치명} |
| 커밋 해시 | {짧은 커밋 해시} |

## 대상
- 기능: {T번호 — 요구사항 한 줄 요약}
- 디렉터리: api/ 또는 web/
- 테스트 파일: {경로}

## 결과
| 완료 기준 | 테스트 | 결과 |
|-----------|--------|------|
| ... | `it(...)` | ✅ 통과 / ❌ 실패 |

## 요약
- 통과 {n}개 / 실패 {n}개
- 아직 테스트가 없는 완료 기준: {있으면 나열, 없으면 "없음"}
```

### 6단계. 보고
- 보고서 경로를 사용자에게 알리고, 통과/실패 요약과 커버하지 못한 완료 기준을 함께 보여준다

## 주의
- 요구사항에 없는 동작을 임의로 테스트에 넣지 않는다
- 테스트를 통과시키기 위해 완료 기준의 의미를 바꾸지 않는다 (기준이 잘못됐다고 판단되면 먼저 사용자에게 확인)
- 보고서는 테스트를 실행할 때마다 새로 만든다 (기존 보고서를 덮어쓰지 않는다 — 같은 날 같은 기능/브랜치로 다시 실행하면 파일명 끝에 `-2`처럼 번호를 붙인다)
