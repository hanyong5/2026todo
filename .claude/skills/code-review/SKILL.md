# 코드 리뷰 (Todo 앱)

대상: 현재 작업 트리의 변경사항(`git diff`) 또는 사용자가 지정한 범위

## 진행 순서

### 1단계. 변경 범위 확인
- `git status`, `git diff`로 변경된 파일을 확인한다
- 변경이 `api/`, `web/`, `docs/`, 루트(워크스페이스/CI 설정) 중 어디에 속하는지 파악한다

### 2단계. 요구사항 대비 검토
- `docs/requirements.md`에서 관련 기능(T/S/N 번호)과 완료 기준을 찾는다
- 완료 기준을 실제로 만족하는지 코드를 보고 확인한다
- `api/` 변경이면 `docs/api-spec.md`(있으면)의 요청/응답 정의와 일치하는지 확인한다

### 3단계. 코드 품질 검토
- 중복/불필요한 복잡도가 있는지 확인한다 (과한 추상화, 쓰이지 않는 분기)
- 에러 처리가 요구사항에 명시된 경우에만 있는지 확인한다 (존재하지 않는 예외 상황에 대한 방어 코드는 과함)
- `api/`, `web/` 각각에서 `npm test`가 통과하는지 확인한다 (현재 lint 스크립트는 구성되어 있지 않다)

### 4단계. 커밋 규칙 검토
- 커밋 메시지가 Conventional Commits 형식(`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`)을 따르는지 확인한다 (CLAUDE.md 참고)
- 커밋 범위가 한 가지 목적에 집중되어 있는지 확인한다 (관련 없는 변경이 섞여 있으면 분리 제안)

### 5단계. 결과 보고
- 발견한 문제를 심각도 순으로 정리해 보여준다: 요구사항 미충족 > 버그 > 품질/스타일
- 문제마다 파일:라인과 어떤 완료 기준/규칙에 위배되는지 함께 적는다
- 문제가 없으면 그대로 보고한다 (없는 문제를 지어내지 않는다)

## 주의
- 요구사항에 없는 기능 추가를 발견하면 범위 초과로 플래그하고, 바로 삭제하지 말고 사용자에게 확인한다
- 스타일 선호 차이(세미콜론 등)는 프로젝트에 정해진 규칙이 있을 때만 지적한다
