# API 스펙 작성 (api/)

결과물: `docs/api-spec.md`

## 진행 순서

### 1단계. 입력 자료 확인
- `docs/requirements.md`를 읽고, 기능 요구사항(T1, S1, N1 …)과 완료 기준을 API 동작의 기준으로 삼는다
- `docs/api-spec.md`가 이미 있으면 먼저 읽고 기존 엔드포인트 번호·경로를 유지한다 (`GET /api/health`가 기본 상태 확인용으로 이미 구현되어 있다)

### 2단계. 질문으로 정보 모으기 (한 번에 3~5개씩, 이미 답이 있으면 건너뛴다)
- 리소스 이름은 무엇인가요? (예: `todo`)
- 각 요구사항이 어떤 HTTP 메서드/경로에 대응하나요? (추천 매핑을 먼저 제안하고 확인받는다)
- 요청/응답 바디에 꼭 필요한 필드는 무엇인가요?
- 입력값 검증 규칙은 무엇인가요? (예: 빈 문자열 금지)
- 에러 상황과 응답 코드는 어떻게 할까요?
- SQLite에 저장할 테이블/컬럼 구조는 무엇인가요?

### 3단계. 스펙 작성
다음 형식으로 엔드포인트별 표를 만든다.

```
## {번호} {리소스} {행동} — 관련 요구사항: T{n}

| 항목 | 내용 |
|------|------|
| 메서드 | GET / POST / PUT / PATCH / DELETE |
| 경로 | /api/todos 또는 /api/todos/:id |
| 요청 바디 | { "title": "string" } |
| 응답(성공) | 200/201 + { ... } |
| 응답(실패) | 4xx + { "error": "..." } |
| 완료 기준 매핑 | requirements.md의 어떤 완료 기준을 만족시키는지 |
```

- REST 관례를 따른다: 목록 조회 GET, 생성 POST, 수정 PUT/PATCH, 삭제 DELETE
- 요구사항에 없는 엔드포인트를 추가하지 않는다 (필요하면 먼저 사용자에게 확인)
- 데이터 모델(필드명, 타입, SQLite 테이블 스키마)은 문서 앞부분에 한 번 정의하고 각 엔드포인트에서는 참조만 한다

### 4단계. 점검
- 모든 필수(🔴) 요구사항에 대응하는 엔드포인트가 있는가?
- 모든 엔드포인트에 성공/실패 응답이 정의되어 있는가?
- 경로·메서드 네이밍이 일관적인가?

### 5단계. 확정
- 엔드포인트 목록과 요구사항 매핑표를 요약해 보여주고 확인받는다
- `test-writer` 스킬이 이 문서를 기준으로 테스트를 작성할 수 있도록 완료 기준 매핑을 비워두지 않는다

## 주의
- 기술 스택은 CLAUDE.md 기준(Node.js/Express, better-sqlite3)을 따르되, 이 문서 자체는 구현 코드가 아니라 스펙만 다룬다
- 인증·서버 저장은 `docs/requirements.md`의 제외 항목에 있으면 이 스펙에도 포함하지 않는다
