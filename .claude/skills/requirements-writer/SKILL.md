# 요구사항 정의서 작성 (Todo 앱)

결과물: `docs/requirements.md`

## 진행 순서

### 1단계. 기존 문서 확인
- `docs/requirements.md`를 먼저 읽고, 이미 있는 내용은 다시 묻지 않는다
- 새 기능을 추가하는 요청이면 기존 번호 체계를 이어서 쓴다 (할 일 관리 T, 데이터 저장 S, 비기능 N — 새 영역이면 적절한 영문 약자를 새로 정한다)

### 2단계. 질문으로 정보 모으기 (한 번에 3~5개씩)
- 이 기능은 한 문장으로 뭘 하나요?
- 완료 기준(테스트로 바로 확인 가능한 조건)은 무엇인가요?
- 데이터는 어디에 저장되나요? (web의 LocalStorage / api 서버+SQLite)
- 우선순위는 필수/권장/나중 중 무엇인가요?
- 이번 범위에서 제외할 부분이 있나요?
- "모르겠다"는 답이 오면 일반적인 선택지 2~3개를 제시하고 고르게 한다

### 3단계. 문서 작성/갱신
- 기존 `docs/requirements.md`의 표 형식(번호 / 요구사항 / 우선순위 / 완료 기준)과 섹션 구성(개요, 사용자 구분, 기능 요구사항, 비기능 요구사항, 제외 항목, 확인 필요, 요약, 변경 이력)을 그대로 따른다
- 우선순위: 🔴 필수(Must) / 🟡 권장(Should) / ⚪ 나중(Later)
- "한 줄에 한 기능", "~할 수 있다" 형식을 유지한다
- 완료 기준은 테스트 케이스로 바로 옮길 수 있을 만큼 구체적으로 쓴다 (예: "입력값이 비어 있으면 추가되지 않는다")
- 기술 선택(어떤 라이브러리를 쓸지 등 구현 방법)은 요구사항에 쓰지 않는다

### 4단계. 점검
- 모든 기능에 완료 기준이 있는가?
- 제외 항목이 "제외 항목" 표에 명시되어 있는가?
- 애매한 표현("빠르게", "적당히")이 없는가?
- 빠진 정보는 "확인 필요" 표에 넣는다

### 5단계. 확정
- 변경된 기능 수, 우선순위별 개수를 요약해 보여주고 확인받는다
- 문서 상단 버전(v0.1 → v0.2 …)과 작성일, "변경 이력"을 갱신한다

## 주의
- MVP 범위를 넘는 기능 요청이 오면 "제외 항목"으로 분리할지 먼저 확인한다
- 완료 기준이 모호하면 추측해서 쓰지 말고 사용자에게 되묻는다
